# Ta-do — Notes & Decision Log

## Current stage
MVP Core is built and live in production (ta-do.vercel.app): capture, archive, library, categories, notes field, Task/Goal rollup, Supabase Auth (magic link + Google), RLS, and the iOS Shortcuts capture endpoint with per-user hashed tokens and a first-run setup walkthrough. Habit/Routine layer and MVP Complete items (altitude changer, period targets, Habit tracking, Goal↔Habit linking) still not started.

## Key decisions made (chronological)
- App job-to-be-done: "tell me what to do next, and let me trust nothing fell through the cracks, at any zoom level."
- Separate app from routein for now; integration/linking to be revisited later, not designed now.
- Entry types: Thought, Goal, Task — same underlying object, type is changeable after capture.
- Archive (not delete): hides from active lists, stays viewable.
- Categories: 4 base pillars (Spiritual, Physical, Psychological, Career) + custom labels (Art, Music to start). Optional at capture, addable/movable later via an action, multi-category allowed, used only for grouping at altitude views — no other planned purpose.
- Altitude view: daily is default (current + next), zoomable to week/month/year. Each altitude shows a computed rollup AND a separately self-set period target — both shown together, not merged.
- AI burnout/workload suggestions (originally MVP idea) demoted to post-MVP — flagged as risky to ship before enough real usage data exists, and framed as a nudge rather than a verdict.
- Auto-grouping of similar entries demoted in favor of explicit category tagging (simpler, more reliable at personal scale).
- Voice capture: iOS Shortcuts action hitting an API endpoint, not deeper Siri/native integration — simplest path given he owns iOS devices.
- Library sort fields trimmed conceptually — start with type + date, expand only if actually needed in use.
- App renamed from working title "Focus App" to **Ta-do**.
- Habit as own entity (not Task + recurrence rule), created via "track as habit" action; streak computed from `completed_at`, not stored.
- Habit tracking gets an additional **Routine** layer on top, modeled after routein: a Routine starts empty, and Habit ids get added to it as Entries are converted — the Routine acts as a filter over "habits currently planned." Visualization can group by recurrence (daily/weekly/monthly). Flagged as still needing thorough design, possibly by referencing routein's actual implementation directly.
- Goals can be checked off like Tasks — own two-state status (ongoing/achieved), separate enum from Task's (open/done).
- Goals can link to multiple Habits (and a Habit can contribute to multiple Goals) — many-to-many via GoalHabit, so a habit's progress can roll up into goal progress.
- Undated/uncategorized Tasks float in the current daily altitude view by default — that's the default view for most users, so nothing should get lost by lacking a date/category.
- Multi-user is a real requirement, not just schema-shaped scaffolding — the app should support multiple people using it simultaneously (like routein), even though only one person uses it today.
- Backend/storage: Supabase, same as routein.
- Security is treated as required before personal/production use, not before MVP — added as its own checklist track so it isn't forgotten once MVP dev starts.
- MVP success metric defined: daily use for 2 consecutive weeks as sole capture point, replacing iOS Notes (personal) and Slack self-DMs/personal chats (work-adjacent), with nothing falling through the cracks — checked subjectively, not via analytics.
- MVP scope split into two tiers, both still "MVP" (neither pushed to Post-MVP): **MVP Core** (brain dump capture, archive, library view, category assignment, iOS Shortcuts endpoint, Task/Goal rollup) is the minimum to start the 2-week trial; **MVP Complete** (altitude changer, period target input, Habit tracking slice, Goal check-off + Goal↔Habit linking) is lower priority but still required before calling the MVP done.
- Auth/RLS floor pulled forward into MVP Core: since real personal data is used from day one, basic Supabase Auth (login) and RLS (per-user_id scoping) ship with MVP Core rather than waiting for the general Security hardening pass. The rest of Security (Shortcuts endpoint token, rate limiting, dependency scanning, data export/deactivation) still waits.
- Auth built as email OTP, then revised twice in quick succession: (1) typed 6-digit code → magic link, because Supabase's default "Magic Link" email template only supports a clickable link, and getting a typed code requires either customizing that template (which itself required setting up custom SMTP — declined as too much setup for personal use right now) or a Send Email Hook (more code, same underlying need for a third-party email sender); magic link needed zero extra config since Supabase's default sender already worked. (2) Added Google OAuth as a second sign-in option, specifically to sidestep email-rate-limit friction hit while testing (Supabase's built-in sender caps at a handful of emails/hour) — no SMTP needed, no rate limits.
- iOS Shortcuts capture endpoint shipped, then redesigned for correctness: original design used one hard-coded `SHORTCUT_USER_ID` + `SHORTCUT_SECRET` pair as Supabase Edge Function secrets, meaning a shared Shortcut would write every capture into the original owner's account regardless of who ran it. Redesigned around a per-user capture token (random, stored hashed) so the same Shortcut structure can be shared and each person swaps in their own token — entries always land in the account the token belongs to.
- Capture token storage hardened: initially stored in plain text on `profiles.capture_token` (readable/copyable from the app at any time). Revised to store only a SHA-256 hash (`capture_token_hash`), matching how passwords/API keys are normally protected — a leaked table no longer hands out usable tokens. Tradeoff accepted: the raw token can only be viewed once, at generation time; losing it means regenerating and updating the Shortcut.
- Added a first-run onboarding walkthrough (shown once per user, based on `profiles.onboarded_at`) that walks through importing a pre-built "Brain Dump" `.shortcut` file, pasting in the personal capture token, and running a live test — the app polls for a specific test-phrase entry and confirms in real time once it arrives, rather than asking the user to check manually. Completes automatically on a successful test, or via a manual "mark complete" button for anyone who wants to skip it.
- Pre-built Shortcut distributed as a directly-hosted `.shortcut` file (in `public/`) rather than through Apple's iCloud share flow, since generating/signing a Shortcut normally requires the Shortcuts app itself (no Xcode/Simulator was available in the dev environment to automate this). Learned along the way: a `.shortcut` file has no internal name field when imported this way — Shortcuts falls back to the downloaded filename as the display name — so the hosted file is named to match the desired in-app name ("Brain Dump.shortcut").
- Deployed to production: GitHub (github.com/Ethan0507/ta-do) for source, Vercel (ta-do.vercel.app) for hosting. Supabase Auth's redirect URL / Site URL configuration needs both the localhost dev URL and the production domain listed, or OAuth/magic-link redirects silently fall back to whichever is set as Site URL.

## Reminders for future sessions
- Container/session state does not persist automatically — re-upload the latest docs at the start of a new session to continue from here.
- Diet/grocery tracking (routein) is being treated as a fully separate concern for now — do not conflate schema/scope discussions unless explicitly revisiting the linking question.
- schema.md is the source of truth; notes.md and checklist.md should be kept in sync with it, not the other way around.
- This dev machine only has Homebrew, not Xcode/iOS Simulator — Node, the Supabase CLI, the GitHub CLI, and the Vercel CLI were all installed via `brew` this session. No simulator-based iOS automation is available; the pre-built Shortcut was hand-built in the real Shortcuts app and its file shared in, not generated here.
- Supabase Auth redirect config lives in **Authentication → URL Configuration** (Site URL + Redirect URLs) — separate from the Google provider's own settings page, and separate again from Google Cloud Console's OAuth client redirect URI (which only ever needs Supabase's own callback URL, never localhost or the app's domain). All three have been a recurring source of confusion.
- Supabase's built-in email sender is fine for personal use but rate-limited to a handful of emails/hour — expect "email rate limit exceeded" during heavy auth-flow testing. Custom SMTP (e.g. via Resend) removes the limit but wasn't set up — deferred as unnecessary for now.
